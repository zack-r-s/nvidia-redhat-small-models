# Frontend handoff prompt for Claude

Build on the existing `frontend/` scaffold as the **read-only visual layer** for a small-model accelerator-control demo. The project specializes Liquid AI's LFM2.5-230M to interpret an operator's request and propose structured control actions. Osprey mediates those actions; its virtual accelerator uses PyAT to compute the actual machine response. The viewer reports the resulting physical state. It never decides an actuator value, predicts a response as fact, or gives the model a way to change the rendered machine directly.

The first control task is orbit correction on a 20-cell FODO storage ring. Four BPMs provide X/Y positions and four horizontal plus four vertical correctors provide bounded steering. The intended judge-facing story is simple: **the beam starts off target; an operator asks the small model to recover it; Osprey executes control actions; PyAT reports the new orbit; the panel shows whether the beam actually reaches the target.** A later comparison may show stock, specialized, and compressed model runs against the same scenario, but this lane only owns their presentation, not inference, optimization, training, or scoring.

Start by reading `README.md`, `data/pv_contract.json`, `src/hackring/api.py`, `src/hackring/machine.py`, `frontend/src/types.ts`, and the current UI. Preserve `hackring.state/1` and the PV names as the current shared contract. The immediate development loop is the local FastAPI/PyAT fixture plus `scripts/xopt_demo.py`; no model server is needed to make the viewer move. Osprey's current in-process simulator and the local API are separate instances. The PyEPICS-backed bridge to a served Osprey virtual accelerator is future integration work, so do not imply the local fixture is already live Osprey data.

## Product and data boundaries

- Render an Osprey URL-backed panel with React, Blueprint, and React Three Fiber. Blueprint owns status, inspection, numerical telemetry, orbit plots, and clear simple/expert labels. Three owns lattice/device geometry and the visual orbit. Aim for a scientific instrument display, understandable without EPICS vocabulary.
- Treat the machine snapshot as authoritative. Use PyAT-provided geometry and reference positions when available. The current `hackring.state/1` snapshot provides circumference, element positions, PV values, and RMS summaries; it does **not** provide a continuous closed-orbit curve, target thresholds, agent events, or benchmark results. Show only the four measured BPM samples until a backend contract supplies more. A circular layout is a schematic, not a claim about the ring's physical floor plan.
- Separate the reference trajectory from measured orbit deviation. Visual magnification is acceptable if labeled plainly (for example, “Orbit deviation ×1000”); numeric values must remain in their true units. Never animate an invented physical response between measurements.
- Keep agent intent, Osprey's reported action status, and actual machine measurements in distinct visual areas. If agent/tool events are not yet available, show an honest unavailable state. Do not fabricate approvals, actions, targets, limits, timestamps, or success.
- The frontend is read-only. It may read a backend endpoint or one-way event stream, but it must not call `/write` or `/scenario`, expose direct machine controls, or let the model mutate display state. Those existing POST endpoints are only for the local test driver and future control integration outside this panel.
- Plan for live, stale/disconnected, and replay states. Replay should consume recorded immutable snapshots through the same rendering components and be visibly labeled. A future unsafe-request demo should distinguish a model proposal from Osprey's actual rejection and the unchanged machine state; only render those facts when event data exists.

## Suggested sequence for this lane

1. Make the current live view solid: four BPM readings in both planes, corrector SP/RB values, meaningful connection/staleness display, unit labels, responsive layout, and an inspectable lattice scene. Keep measured samples visually distinct from any future interpolated or full-orbit data.
2. Define small optional contracts for targets and agent events with the backend teammate before displaying them. An absent field should yield an explicit unavailable state. A goal indicator should be computed from authoritative target and measurement values, never from a decorative animation.
3. Add a replay adapter that feeds the same view from timestamped snapshots, then prepare a deterministic demo fixture. Keep run/model IDs and scenario seeds visible when available so live and replay are distinguishable.
4. Create the Osprey URL-panel manifest and document how to mount the frontend. Keep evaluation-result visuals as a later integration point that consumes a shared result record rather than inventing scores in the UI.

Run `npm run build` before handing the lane back. Exercise the viewer with the README's local API/Xopt commands, and include a screenshot or concise visual QA notes covering desktop, small screen, disconnected state, and how you checked that displayed readings match `/state`. Do not start training or data generation as part of this work.
